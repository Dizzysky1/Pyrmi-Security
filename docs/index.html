Pyrmi Security protects a web game's scores in two halves. A browser script starts a signed session for each run and reports cheat signals. Your server then asks Pyrmi for a verdict before it saves the score. You need both: the browser half alone protects nothing, because a cheater controls their own browser.

Quick start

  1. Create a project on the dashboard. You get a public key (pk_...) and a secret key (sk_...), shown once.
  2. Put the secret key in your server's environment as PYRMI_SECRET_KEY. Never put it in your page.
  3. Add the script tag and three calls to your game, then one verify call to your score endpoint.

Browser script

html 
<script src="https://pyrmi.com/sdk/pyrmi.js" data-site="pk_..."></script>
callwhen
await Pyrmi.start()When a run begins. Returns { token, seed, session, expiresAt }. Each token is good for one score.
Pyrmi.mark(seconds)Optional, about once a second during play: your game's own clock. Lets the server catch speed and slow-motion hacks.
await Pyrmi.flush()When the run ends, before you send the score. Sends the last telemetry.
Pyrmi.report()What the script has noticed so far, if you want to show players what's checked.

Then send run.token to your server along with the score. The script watches for webdriver and headless browsers, bot frameworks, scripted input events, inhumanly fast or even key timing, replaced built-ins like performance.now, a page clock that doesn't match real time, and probably-open devtools. It sends this as small beacons every 10 seconds while the tab is visible.

Server check

node · npm install pyrmi-server 
const { Pyrmi } = require('pyrmi-server');
const pyrmi = new Pyrmi({ secretKey: process.env.PYRMI_SECRET_KEY });

const v = await pyrmi.verify({ token, score, durationMs, player });
if (v.verdict === 'reject') return res.status(400).json({ error: 'score rejected' });
saveScore(player, score, { flagged: v.verdict === 'review' });

Not on Node? It's one HTTPS call from your server:

any language 
curl https://pyrmi.com/api/v1/verify \
  -H "Authorization: Bearer $PYRMI_SECRET_KEY" \
  -H "Content-Type: application/json" \
  -d '{"token":"...","score":123,"durationMs":45000,"player":"alice"}'

If Pyrmi can't be reached, pyrmi-server rejects by default. Pass failOpen: true to accept unverified scores instead.

Replay check (strongest)

If your game is deterministic, meaning the same seed and the same inputs always give the same result, record the inputs during a run and send them with the score. Seed your game's RNG with run.seed so nobody can practise a run in advance. On the server, pass a simulate function that re-runs the game:

node
const v = await pyrmi.verify({
  token, score, durationMs, player, replay: inputs,
  simulate: (inputs) => runGame(seed, inputs),   // returns { score, durationMs }
});

A memory edit, an invincibility hack or a typed-in score won't reproduce, so the verdict is reject with replay_mismatch. The Vessel on the homepage works this way: its engine runs in both the browser and the server, using only math that gives identical results everywhere.

Verdicts and reasons

Each verify returns accept, review (accepted, flagged on the dashboard) or reject, plus a risk from 0 to 100. Hard reasons reject on their own. Soft signals add up.

reasoneffectmeaning
invalid_tokenrejectToken missing, forged or edited.
token_reusedrejectThe same session was already used for a score.
expired / wrong_projectrejectOld token, or one from another game.
impossible_timerejectThe run claims to be longer than its session has existed.
score_over_max / score_too_fast / too_shortrejectBreaks a limit you set.
replay_mismatchrejectReplaying the inputs gave a different result.
rate_limitedrejectToo many scores from one player in a minute.
automation+70Webdriver, headless or a bot framework. Real players never have these, so this alone rejects at the default settings.
no_client+40No telemetry ever came from a real page: a direct API call.
synthetic_input+40Input events created by script.
speed_hack / time_warp+35Page or game clock out of step with real time.
tampered_runtime+30Built-in functions replaced. Some analytics and error tools wrap fetch, so this one alone only adds risk.
inhuman_input+25Input too fast or too regular for a hand.
ua_changed / idle_input+20 / +15Browser changed mid-session / long run with almost no input.
devtools_open / ip_changed+10Weak hints, worth a look only alongside others.

Settings

On the dashboard: max score, max score per second, shortest run, the risk levels for flagging (default 40) and rejecting (default 70), the pages allowed to start sessions, and whether to flag games that run slower than real time. You can also make a new secret key there if yours leaks.

Set it up with an AI agent

Hand your coding agent install.md. It's written for agents like Claude Code and Cursor, step by step, and tells them to keep your secret key out of the code.

Self-hosting

Everything is MIT, so you can run your own copy: deploy the repo to Vercel, add a free Upstash Redis from Vercel's Storage tab (it sets KV_REST_API_URL and KV_REST_API_TOKEN), and set PYRMI_SECRET to a long random string. Then point the script at it with data-api="https://your-deploy/api/v1" and pyrmi-server with endpoint. For local work: PYRMI_KV=memory node scripts/dev.js.

Limits, honestly

Pyrmi can't block devtools or stop code running in a player's browser, and nothing can: the player owns that browser. A determined cheater can hide most browser signals. What they can't fake is a signed, single-use session, a run that fits the real time it took, and, for deterministic games, inputs that reproduce the score. Treat browser signals as evidence, and let your server's verdict be the gate.
